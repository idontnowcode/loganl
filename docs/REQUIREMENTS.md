# 요구사항 추적표와 검토 — Local Log Analyzer

- 기준 문서: [DEV_PLAN_v0.2_R01.md](DEV_PLAN_v0.2_R01.md) (LLA-DEV-PLAN-001 v0.2 R01). 이 표는 계획서를 대신하지 않는다. 충돌하면 계획서가 이긴다.
- 계획서 이후 사용자가 더한 요구사항은 변경 요청(CR)으로 §1.16에 둔다. 현재 CR-01(대응 매뉴얼·권장 대응), CR-02(화면 디자인·가독성, 기능 변경 없음), CR-03(다른 PC 무설치 실행), CR-04(참고 자료·코드 사전), CR-05(칸 대신 자연어로 적기), CR-06(로그 입력 탭 하나로), CR-07(LLM 질문·확률 의견) 7건.
- 작성: 2026-11-16, Phase 1 착수 시점.
- 상태 표기 (2026-11-17 Phase 9 기준으로 갱신)
  - **구현**: 코드와 자동화 테스트로 충족함 (검증 열의 테스트 참조)
  - 아래는 Phase 1 당시 표기
  - **P1 구현**: 이번 Phase 1 코드와 테스트로 충족함
  - **P1 기반**: Phase 1에서 스키마·설정·구조만 준비함. 기능은 표시된 Phase에서 구현
  - **Pn**: 해당 Phase에서 구현 예정. 아직 코드 없음
  - **미정**: 사용자 답이 필요함(§3 질문 참조)
- 검증 열의 `T-…`는 [TEST_PLAN.md](TEST_PLAN.md)의 시험 ID, `test_…`는 실제 테스트 파일이다.

### 1.22 변경 요청 CR-07 — LLM이 묻고 배우고, 확률로 의견 (2026-11-17 사용자 요청)

> 사용자 요청 요지(원하는 흐름 7가지): ① 로그 입력 탭에 로그 업로드 ② 파일마다 정상/비정상(필수) ③ 로그별 메모(선택) ④ 비정상이면 판단 가이드(선택) ⑤ 이슈 정보 라이브러리(에러 코드 리스트 등, 선택) ⑥ **LLM이 스스로 판단 능력을 갖도록 사용자에게 질문**(모르는 것, 자기 추측이 맞는지 등) ⑦ 로그를 쌓아 가면서 분석 탭에 로그를 올리면 **LLM이 분석하고 확답이 아닌 확률로 의견**. 가져오기 옵션 구역(수집 세션·파서 등)은 "의미가 없는 것 같다".
> 질문 답: LLM 질문은 **저장할 때마다 + 질문함**, 확률은 **% 숫자 + 근거**, 라이브러리는 **코드표 + 일반 문서**.
> 계획서와 다른 점: ④ 비정상 판정 기준이 승인 필수였다(§3.2, AL-09) → 선택. ⑦ 계획서는 유사도 점수를 확률로 보이지 말라고 했다(NA-13) → 그대로 지키고, **AI가 스스로 매긴 가능성**을 'AI 추정치(통계 확률 아님)'로 따로 보인다. 지키는 것: 정상·비정상은 사용자가 고름, AI는 오류 코드 뜻을 단정하지 않음, 근거 키 검증, 승인된 지식만 사용.

이 변경으로 정한 기본값:

- 0001의 CHECK 제약 하나만 SQLite 공식 절차(writable_schema로 CREATE TABLE 문에서 제약 문구 삭제)로 뺀다. 표를 다시 만들지 않는다(외래 키가 걸린 표가 많아 다시 만들면 연쇄 삭제 위험). 제약을 **느슨하게만** 하므로 기존 데이터는 그대로 맞는다.
- AI 질문은 사용자가 고른 정상/비정상을 바꾸지 않는다. 답은 사례 승인과 별개로 바로 지식이 된다(사용자가 직접 답한 것이므로).

### 2.3 구현상 위험

| # | 위험 | 대응 |
|---|---|---|
| K-1 | **CPU 전용 추론 속도.** 7~8B 양자화 모델을 CPU로 돌리면 초당 몇 토큰 수준이라 분석 한 번에 몇 분이 걸릴 수 있다. | 근거 패키지 크기 제한, 스트리밍, 취소. Phase 7 전에 사내 PC에서 실제 속도를 측정한다. |
| K-2 | **컨텍스트 길이.** 10MB × N개 로그는 모델에 통째로 넣을 수 없다. | 계층 1·2가 고른 근거만 전달한다(계획서 설계와 같음). |
| K-3 | **로그 형식 미확인.** 샘플 없이 만든 파서는 추측이 된다. | 범용 파서는 정규식 프로파일로만 동작하게 하고, 실제 형식은 프로파일로 추가한다. Phase 2 전에 샘플이 필요하다(Q4). |
| K-4 | **사례가 적을 때 AI 판정.** 처음에는 AI가 정상·비정상을 구분할 근거가 거의 없다. | AI는 등록된 모드 중에서만 고르고 UNKNOWN을 허용한다. 결정은 사용자가 한다. 계층 1의 결정론 비교를 주 근거로 쓴다. |
| K-5 | **사내 PC 오프라인 설치.** Python·PySide6·Ollama 모델을 반입해야 한다. | Phase 9에 PyInstaller 실행 파일. 그 전에 사내 PC에서 시험하려면 uv로 wheel 묶음을 따로 만든다. |
| K-6 | **사내 프록시.** `HTTP_PROXY` 환경 변수가 있으면 httpx가 localhost 요청도 프록시로 보낼 수 있다. | httpx를 `trust_env=False`로 만든다(Phase 1 구현). |
| K-7 | **SQLite 버전 차이.** STRICT 테이블은 3.37 이상, FTS5는 빌드 옵션이 필요하다. | 시작할 때 기능을 검사한다(Phase 1 구현). 실행 파일에는 SQLite가 함께 들어간다. |
| K-8 | **이벤트 행 수.** 10MB 파일 하나가 약 10만 줄이면 10개 파일은 100만 행이다. | Phase 2에서 일괄 삽입과 색인을 쓰고 성능 테스트(T-PERF-01)를 한다. |
| K-9 | **개발 PC 한정: MSIX 가상화.** Claude 데스크톱 앱 안에서 실행한 프로세스가 `%LOCALAPPDATA%`에 쓰면 앱 전용 공간으로 가상화된다. | 테스트는 `LLA_HOME` 환경 변수로 임시 폴더를 쓴다. 사용자가 직접 실행할 때는 영향이 없다. |
| K-10 | **바이너리 CAN 로그.** 검토 의견은 CAN 로그를 언급하는데, 계획서 입력은 TXT/LOG뿐이다. | 텍스트로 변환된 CAN 로그만 범위에 넣는다. 바이너리 형식이 필요하면 요구사항 추가가 필요하다(Q4). |
| K-11 | **PySide6 라이선스(LGPL).** 사내 배포할 때 고지가 필요하다. | Phase 9 패키징 때 고지 파일을 포함한다. |
