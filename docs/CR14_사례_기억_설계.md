# CR-14 사례 기억 — 확인된 로그가 쌓일수록 정확해지는 구조 (설계, 2026-11-22)

## 1. 요청과 목표

- 사용자: "앱의 판단을 로그에 맞게 고치는 게 아니라, 로그가 쌓일수록 Ollama가 더 정확한 판단을 하게끔 하는 구조여야 해."
  "규칙을 두든 되돌리든, **앱 업데이트 없이** 개발 장비의 로그를 쌓을수록 분석 정확도가 올라가는 구조면 돼."
- 지금 구조의 한계(2026-11-22 측정, `TEST_PLAN` 기준선):
  - 판정은 결정론 규칙이 하고, AI(gemma3:4b)는 규칙 판정을 거의 그대로 따라감(의심 75~85%, 규칙 오탐에도 85%).
  - AI에 주는 '비슷한 비정상 사례'는 전체 이벤트 종류로 찾아서, 오류 코드 없는 고장은 같은 종류가 1등인 경우가 절반.
  - 엔지니어가 분석 결과를 확인해도 그 결과가 다시 쓰이지 않음(분석 → 학습으로 이어지는 길이 없음).
- 목표: **확인된 로그(사례)가 쌓이는 것만으로** 판정과 AI 의견이 나아진다. 코드·규칙·문턱을 사람이 다시 고치지 않는다.
- 합격 기준(측정 도구 §6):
  1. 스트림 시뮬레이션에서 확인 사례가 쌓일수록 정확도가 오르고, 같은 스트림의 '규칙만'보다 높다(다중 챔버·CT·무작위 제품군).
  2. 확인 사례가 없거나 적으면 지금과 똑같이 동작한다(기존 회귀 세트 결과 그대로).
  3. AI 의견: 같은 대상에서 사례 기억을 준 뒤 가능성 판단이 정답 쪽으로 움직이고, 가설에 확인된 원인을 근거로 쓴다.

## 2. 원칙

- 모델 재학습(파인튜닝)은 하지 않는다(오프라인 CPU 사내 PC). 쌓인 데이터는 **검색·투표·실적**으로만 쓴다.
- 뜻을 지어내지 않는다. 사례의 원인 글은 엔지니어가 쓴 글 그대로 AI 근거로 준다.
- 사례 기억이 규칙 판정을 바꾸면 그 이유(어느 확인 로그와 어떤 근거가 같았는지)를 근거 목록에 남긴다.
- **DB 구조는 바꾸지 않는다**(스키마 7 유지). 근거 지문은 로그와 사례로 언제든 다시 계산할 수 있는 캐시다.

## 3. 구성

### 3.1 근거 지문 (`app/learning/case_memory.py`)
- 로그 하나의 결정론 근거(규칙이 찾은 차이)를 **위치·값을 뺀 특징 문자열 집합**으로 바꾼다.
  - 예: `EXPLICIT_ERROR:TEST-E710`, `VALUE_OUT_OF_RANGE/value_groups:temp@T-CHA|TEL pressure=<N> temp=<N> sub=W0<N>`,
    `ORDER_VIOLATION/flow:sub`, `MISSING_EVENT/component_absent_unexplained:T-CHC`, `EXTRA_EVENT:<본 적 없는 이벤트 유형>`.
  - 강한 특징(규칙이 '의심'으로 본 근거, stance SUPPORTS)과 약한 특징(참고로만 본 근거)을 나눠 둔다.
- 함께 둔다: 그때 규칙 판정(anomaly_level), 지문을 만들 때 저장돼 있던 정상 사례 수.
- 저장: 데이터 폴더 `analysis/fingerprints/<log_file_id>.json`(캐시). 분석할 때마다 그 로그의 지문을 남긴다.
  정상 사례 수가 만들 때보다 25% 넘게 늘었거나 지문 형식 번호가 바뀌면 다시 만든다.

### 3.2 사례 기억
- 확인된 로그 = 승인된 단일 로그 사례(정상·비정상). 사례마다 지문이 없으면 그 로그를 정상 사례들과 다시 비교해 만든다
  (자기 사례는 비교 기준에서 뺌). 분석 한 번에 지문 만들기는 시간 예산(20초) 안에서만, 남은 것은 다음 분석 때.
- 유사도: 특징마다 무게 = 드문 정도(확인 로그 중 그 특징이 있는 로그가 적을수록 큼, IDF). 가중 자카드.
- 근거별 실적: 특징마다 '확인된 비정상 n·정상 m'에서 나옴.

### 3.3 사례 판단 (규칙 판정 보정)
- 이웃: 이 로그와 유사도 τ 이상인 확인 로그. 유사도로 가중한 투표 → 비정상 비율 p.
- 보정(규칙 판정 → 최종 판정). 이웃 유사도 합이 1.0 이상일 때만(덜 비슷한 사례 하나로는 바꾸지 않음, 2026-11-22 애매한 세트 MC_031):
  - 규칙 '의심' + p ≤ 1/3 + 이 로그의 강한 특징이 모두 이웃 정상 로그에도 있었음 → '찾은 이상 없음'
    (근거: "확인된 정상 로그 C-0031과 같은 차이").
  - 규칙 '찾은 이상 없음' + p ≥ 2/3 → '의심'(근거: "확인된 비정상 로그 C-0012와 근거 지문이 같음, 원인: …").
  - 승인된 규칙 위반(RULE_VIOLATION)은 바꾸지 않는다.
- **스스로 문턱 고르기(앱 업데이트 없이)**: 확인 로그마다 '그 로그를 빼고 나머지로 판단'(leave-one-out)을 해서
  τ ∈ {0.3, 0.4, 0.5, 0.6, 0.7} 중 균형 정확도(정상·비정상 각각 맞힌 비율의 평균)가 가장 높은 것을 고른다.
  그 값이 규칙만의 균형 정확도보다 높을 때만 보정을 쓴다. 확인 로그가 정상·비정상 각 3개 미만이면 쓰지 않는다.
- 결과 화면·보고서·AI 요약에 "사례 판단: 근거가 비슷한 확인 로그 k개 중 비정상 a·정상 b(유사도 …), 사례 기억 자체 점검 정확도 …"를 남긴다.

### 3.4 AI 근거
- 이웃 확인 로그(판정·원인 글·유사도·같았던 근거)를 근거 목록 **앞쪽**에 CASE로 넣는다(지금의 '비슷한 사례'보다 먼저).
- 이 로그 특징들의 근거별 실적을 한 줄씩 FINDING 근거로 넣는다("이 근거는 확인된 로그 중 비정상 3·정상 0에서 나옴").
- 지시문 7)에 한 줄 추가: "근거 지문이 비슷한 확인 로그의 판정·원인과 근거별 실적을 가장 중요하게 본다."

- '비슷한 비정상 사례'(전체 이벤트 종류로 찾은 것)는 오류 코드가 같거나 가장 비슷한 정상 사례보다 더 비슷할 때만 이상 쪽 근거(SUPPORTS)로
  준다. 같은 제품 로그는 이벤트 종류가 거의 같아 정상 로그에도 붙어 AI가 끌려갔다(2026-11-22 측정: 사례 기억 없이 AI 정답률 70%→32%).

### 3.4.1 AI 판정 보정 (CM-07)
- 분석할 때 AI가 낸 비정상 가능성을 그 로그의 지문에 함께 남긴다. 그 로그가 나중에 확인되면 'AI가 몇 %라고 했는데 실제로는 무엇'이 이력이 된다.
- AI 의견이 있던 확인 로그가 정상·비정상 각 3개 이상이면, 문턱 50~95%(5% 간격) 중 균형 정확도가 가장 높은 것을 고른다(같으면 50%에 가까운 쪽).
  'AI 판정(확인 이력 보정)'으로 보이고 결과 메모·AI 칸에 이유를 적는다. AI 모델이 가능성을 한쪽으로 쏠리게 내도 쌓인 확인 결과로 맞춘다.
- 측정 근거(다중 챔버, 학습 100 → 시험 50): gemma3:4b가 비정상은 대부분 85%, 정상은 0~85%로 냄 → 문턱 50%면 균형 68%, 85%면 83%.

### 3.5 확인 결과 남기기 (분석 → 사례)
- 신규 분석 ②에 '확인 결과 남기기': [정상이었음] [비정상이었음] + 원인·메모(비정상이면 필수) → 그 로그를 사례로 저장
  (`LogEntryService.save`, 지금 학습과 같은 경로) + 그 분석의 지문을 그대로 사례 지문으로.
- 학습 탭에서 저장한 로그도 똑같이 사례 기억에 들어간다(지문은 §3.2처럼 나중에 계산).

## 4. 하지 않는 것
- 모델 재학습·외부 네트워크·코드 뜻 지어내기. 수량 숫자 비교(기판 하나 빠짐) 같은 새 규칙.

## 5. 영향
- 확인 사례가 없거나 한쪽뿐이면 지금과 같다(§3.3 조건). 기존 4폴드 평가는 정상만 저장하므로 결과가 그대로여야 한다.
- 분석 시간: 지문은 이미 나온 근거로 만든다. 사례 기억 계산은 집합 연산(수백 개 × 수십 특징). 분석 없이 저장된 사례의 지문은
  한 번 만들어 캐시.

## 6. 측정 도구 (시험 방법은 사용자 지정, 2026-11-22)
- 샘플을 **학습용 100개·시험용 50개**로 따로 만든다(`make_cluster_tool_samples.py --total 50 --seed …`, 또는
  `split_train_test.py`로 한 세트를 나눔).
- `samples/evaluate_learning.py <학습> <시험>`: 학습용 100개를 모두 사례로 저장 → 시험용 50개를 하나씩 분석하고 정답으로 '확인 결과 남기기'.
  10개마다 누적 정답률(규칙만·최종·AI·AI 보정). `--no-memory`로 사례 기억을 끈 같은 시험과 비교, `--ai`로 AI까지.
- 애매한 세트(`--ambiguous`): 줄 모양이 같고 코드만 다른 INFO 알림 두 가지(문제없는 TEST-FA, 점검 필요 TEST-FK)를 섞는다.
  오류·경고가 아니어서 규칙은 뜻을 모르고, 확인된 이력으로만 가를 수 있는 경우(실제 장비 로그에 흔함).

## 8. 리뷰 반영 (2026-11-22, 사용자가 다른 AI 검토 화면을 첨부)

| 지적 | 고친 것 |
|---|---|
| 정상 로그에도 승인된 비정상 대응 매뉴얼이 함께 표시됨, AI가 증상 문서 근거 번호로 미등록 조치 문장을 씀 | 권장 대응은 최종 판정이 비정상 쪽 + 적용 근거(근거 지문 0.5 이상 또는 같은 오류 코드)가 확인된 사례만, 다른 단계면 '재확인'. AI 대응 항목은 RESPONSE 키 필수, 화면 문장은 조치 원문(CM-08) |
| AI가 가능성을 매기지 않았는데 '정상 쪽'으로 표시, 판정이 여럿 | 최종 판정 하나(정상/비정상/판단 보류)와 보류 사유, AI 판정도 보류 가능, 보고서·측정 반영(CM-09) |
| 지문을 다시 만들면 과거 AI 점수가 지워짐, 결과 화면에서 다시 저장하면 운전 조건 메모가 지워짐 | AI 점수 옮겨 두기, 메모 지키기(CM-10) |
| 같은 수집 세션 묶음 분석에는 확인 버튼·사례 기억 보정이 빠짐 | 사례 기억 단위를 로그 묶음으로, 묶음을 사례 하나로 저장(CM-11) |

- 리뷰의 판단(가상 데이터에서 사례 기억 효과 확인, 47/50 → 49/50)은 우리 측정(애매한 세트 94% → 98%)과 같다.
- 리뷰가 권한 다음 단계: 실제 장비 로그로 고정 시험 세트를 두고 사례 등록 전후의 비정상 누락률·정상 오탐률·판단 보류율·잘못된 대응 표시 건수를 비교.
  → `samples/split_train_test.py`(학습·시험 나누기) + `samples/evaluate_learning.py`(학습 → 시험 하나씩 분석·확인)로 바로 잴 수 있다.

## 9. AI는 설명 보조로 (2026-11-22 사용자 결정)

- 측정(학습 100 → 시험 50, 애매한 세트): 규칙 94%, 규칙+사례 기억 98~100%(판단한 것), AI(gemma3:4b) 원래 50~65%, 확인 이력 보정 64%.
  AI만으로 건 '판단 보류' 6건 중 5건이 정상(모델이 깨끗한 정상 로그에도 85%를 자주 냄).
- 결정: 최종 판정은 규칙 + 사례 기억으로만. AI 판정(확인 이력 보정 포함)은 화면·보고서에 설명으로 따로 보이고 판정을 바꾸지 않는다.
- 가상 로그는 이름이 모두 뜻 없는 TEST-라 언어 모델에게 불리한 시험이다. 실제 장비 로그(사람이 읽는 낱말)·7~8B 모델로 다시 재서 역할을 넓힐지 정한다.
