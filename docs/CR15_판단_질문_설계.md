# CR-15 판단 질문 — 애매할 때 사용자에게 물어 판정 근거를 모으기 (설계, 2026-11-22)

## 1. 요청과 목표

- 사용자: "AI의 역할은 판단 보류나 정확성이 떨어지는 경우, 사용자에게 판단 방법 등에 대한 질문을 던져
  판단 알고리즘으로 판단이 가능한 근거 데이터를 수집하는 것은 어떤지?" → "진행".
- 배경(CR-14 측정): 판정은 규칙 + 사례 기억(코드)이 하고, AI(gemma3:4b)는 판정에 넣지 않기로 함(설명 보조).
  사례 기억은 비슷한 확인 사례가 몇 건 쌓여야 판정이 바뀐다. 오류 아닌 알림·처음 보는 차이처럼
  **규칙이 뜻을 모르는 근거**는 확인 사례가 쌓이기 전까지 '판단 보류'나 놓침이 된다.
- 목표: 애매한 분석에서 엔지니어에게 짧게 묻고, 답을 **코드 판정이 그대로 쓸 수 있는 기준**(이 줄이 나오면 비정상 /
  이 차이는 문제없음 / 이 값은 몇까지 정상 …)으로 저장한다. 답 하나가 비슷한 사례 여러 건 몫을 하게 해 학습을 앞당긴다.
- 기존 CR-07(저장할 때 AI 질문)과의 차이: CR-07의 답은 글로 남아 AI 근거로만 쓰인다. CR-15의 답은 구조화된 **판단 기준**이 되어
  규칙 + 사례 기억 판정에 직접 들어간다.
- 합격 기준(사용자 지정 시험 방법, 학습 100 → 시험 50): 정답표로 답하는 '가상 엔지니어'가 질문에 답할 때와 안 답할 때를 비교해
  **판단 보류 비율이 줄고 정답률이 같거나 오른다**. 질문이 없거나 답이 없으면 지금(v0.7.0)과 똑같이 동작한다.

## 2. 원칙

- 판정은 코드가 한다. 장비 지식은 **엔지니어의 답에서만** 들어온다(뜻을 지어내지 않음).
- 질문의 틀은 코드가 근거(근거 지문 특징)에서 만든다. AI는 없어도 동작하고, 있으면 질문 문장을 다듬거나 자유 답을
  기준 후보로 정리하는 것만 한다(사용자가 확인해야 저장).
- 답으로 만든 기준도 확인된 로그에서의 실적을 계속 세고, 스스로 점검에서 정확도를 떨어뜨리면 쓰지 않는다(잘못된 답 막기).
- 묻는 건 짧게: 애매한 분석에서만, 한 번에 최대 3개, 언제든 건너뛸 수 있다.

## 3. 구성

### 3.1 언제 묻나 (JQ-01)
- 최종 판정이 **판단 보류**이거나,
- 판정은 났지만 그 판정을 만든 근거 특징(근거 지문)에 **확인 이력이 없는** 것이 있을 때
  (예: 규칙이 '참고'로만 본 처음 보는 알림 줄, 정상 범위 밖이지만 확인된 적 없는 값, 확인된 정상에도 있었는지 모르는 빠짐).
- 이미 기준이 있는 특징, 확인 이력이 한쪽으로 뚜렷한 특징(같은 판정 3건 이상)은 묻지 않는다.

### 3.2 무엇을 묻나 (JQ-02) — 근거 특징 종류별 질문 틀
| 근거 특징 | 질문(예) | 답 → 기준 |
|---|---|---|
| 처음 보는 줄·새 경고(EXTRA_EVENT·new_warning) | "이 줄(원문)이 나오면 문제인가요?" | 문제의 표시 → **비정상 표시** / 정상에서도 나옴 → **문제없음** |
| 오류 코드(EXPLICIT_ERROR) | "오류 코드 X는 실제 문제를 뜻하나요?" | 문제 → 비정상 표시 / 알려진 무해 코드 → 문제없음 |
| 값 범위·값 무리 이탈(VALUE_OUT_OF_RANGE) | "'temp' 값 442는 정상 범위를 벗어난 것인가요? 정상 범위를 알면 적어 주세요" | 벗어남 → 비정상 표시 / 정상 → 문제없음 / 숫자 → **값 기준**(하한·상한) |
| 빠짐·구성요소 빠짐(MISSING_EVENT) | "X가 없는 것은 문제인가요?" | 문제 / 정상 운전에서도 빠질 수 있음 |
| 순서·흐름(ORDER_VIOLATION·flow) | "B가 A보다 먼저 나온 것은 문제인가요?" | 문제 / 순서가 바뀌어도 됨 |
| 반복·간격(REPETITION·LATENCY) | "같은 줄이 N번 연달아 나온 것은 문제인가요?" | 문제 / 문제없음 |
- 모든 질문에 공통 답: **상황에 따라 다름**(→ '사람 확인 필요' 기준: 이 특징이 나오면 판단 보류), **모름**(저장 안 함),
  **판단 방법(선택, 글)**: 엔지니어가 어떻게 판단하는지 적으면 AI가 기준 후보로 정리해 보여 준다(§3.5).
- 질문 고르기: 판정에 영향이 큰 것부터 — 보류 사유가 된 특징 → 강한 근거 특징 → 드문 특징(IDF 큰 것).

### 3.3 판단 기준 저장 (JQ-03) — DB 마이그레이션 0008(스키마 8)
- 새 테이블 `judgment_criteria`: 특징 글자(근거 지문과 같은 열쇠), 기준 종류(ABNORMAL_SIGN / BENIGN / VALUE_RANGE / HOLD),
  값 기준(하한·상한), 질문 글·답·답한 로그·분석 번호(출처), 상태(ACTIVE / DISABLED), 끈 이유, 만든 시각.
- 기준은 사용자 지식이므로 캐시가 아니라 DB에(백업·복원 대상). 같은 특징에 기준은 하나(새 답이 이전 것을 대신, 이력은 감사 기록).

### 3.4 판정에 쓰기 (JQ-04)
- 사례 기억 판단(CR-14) 앞에서 기준을 먼저 본다.
  - **비정상 표시** 특징이 로그에 있으면 → 비정상 의심(이유: "사용자 기준: ‘…’이 나오면 비정상").
  - 규칙이 의심한 강한 근거가 모두 **문제없음** 기준(또는 확인된 정상 이력)에 해당하면 → 정상(이유 함께).
  - **값 기준**: 그 이벤트의 그 값 칸이 사용자 범위를 벗어나면 비정상 의심, 범위 안이면 그 값 근거를 '문제없음'으로.
  - **사람 확인 필요** 특징이 있으면 → 판단 보류(이유: "이 차이는 상황에 따라 다르다고 답함").
- 기준끼리 부딪히면(비정상 표시와 문제없음이 함께) 판단 보류.
- 결과 메모·보고서에 어떤 기준이 판정을 정했는지 적는다.

### 3.5 AI의 역할 (JQ-05, 선택)
- 질문 문장 다듬기: 질문 틀 + 원문 줄을 엔지니어가 읽기 쉬운 한 문장으로(뜻 추측 금지, 원문 낱말만).
- 자유 답 정리: '판단 방법' 글을 기준 후보(종류·특징·숫자)로. 숫자는 사용자 글에 있는 것만, 특징은 이 로그 근거에 있는 것만(검증).
  후보를 화면에 보이고 사용자가 '기준으로 저장'을 눌러야 저장.
- AI가 꺼져 있으면 질문 틀 그대로 묻고, '판단 방법' 글은 CR-07처럼 글 지식으로만 남긴다.

### 3.6 잘못된 기준 막기 (JQ-06)
- 기준마다 확인된 로그(사례)에서의 실적: 그 기준이 판정을 정한 로그 중 확인 판정과 맞은 수·틀린 수.
- 스스로 점검: 확인 로그로 '기준 쓰기 vs 안 쓰기'를 견줘 정확도를 떨어뜨리는 기준은 자동으로 끄고(DISABLED) 이유를 남긴다.
- 관리 화면(데이터 관리 → 판단 기준): 기준 목록(읽기 쉬운 특징·종류·출처·실적·상태), 끄기·켜기·지우기.

### 3.7 화면 (JQ-07)
- 신규 분석 ② '확인 결과 남기기' 위에 **판단을 돕는 질문** 칸(질문이 있을 때만): 질문마다 원문 줄(두 번 누르면 원본 행), 답 단추,
  값 질문은 숫자 칸, 공통 '판단 방법' 글 칸. 답하면 바로 기준으로 저장하고 '다시 분석'을 제안한다.
- 학습 ③(저장·AI 질문)의 기존 CR-07 질문은 그대로 둔다.

## 4. 하지 않는 것
- AI가 판정하기, AI가 기준을 혼자 만들기, 뜻 지어내기, 모든 분석에서 묻기, 수량 숫자 관계 같은 새 규칙.

## 5. 영향
- DB 스키마 7 → 8(마이그레이션 0008, 테이블 추가만). 한 번 v0.8로 연 데이터는 예전 앱으로 열지 않는다(지금까지와 같은 안내).
- 기준이 하나도 없으면 판정은 v0.7.0과 같다. 분석 시간: 기준 확인은 집합 비교와 값 칸 한 번 읽기.

## 6. 측정 (JQ-08)
- `samples/evaluate_learning.py --answer-questions`: 시험 로그를 분석한 뒤 질문이 나오면, 정답표를 아는 가상 엔지니어가 답한다.
  - 그 로그가 정상 → 물은 특징은 '문제없음'.
  - 그 로그가 비정상 → 특징이 정답표 판단 가이드의 낱말(예: TEST-FK, temp)과 겹치면 '비정상 표시', 아니면 '모름'.
  - 그다음 지금처럼 '확인 결과 남기기'.
- 같은 학습 100 → 시험 50에서 질문 답 켬·끔의 정답률·판단 보류 비율·질문 수를 비교(애매한 세트·다중 챔버 세트).

## 9. 구현 메모 (2026-11-22)

- `app/learning/criteria.py`(질문 틀·기준 적용·스스로 끄기·`CriteriaService`), `app/storage/migrations/0008_judgment_criteria.sql`,
  `CriteriaRepository`, 엔진(`_questions`, 사례 기억 뒤 `apply_criteria`, 근거 TEXT_MATCH role CRITERION), 최종 판정(`criteria.hold_decisive`·이유),
  화면 `app/ui/question_box.py`(② 질문 칸, '이 로그 다시 분석'), `app/ui/criteria_dialog.py`(데이터 관리 → 판단 기준).
- 질문 조건: 강한 근거 중 이력이 없거나 엇갈린 것 → 판단 보류면 약한 근거도, 판정이 났으면 이력 없는 처음 보는 줄(EXTRA_EVENT)만. 최대 3개.
- 값 범위 기준은 그 이벤트의 그 값 칸을 직접 읽어 판정한다(규칙이 못 잡은 값도 잡음). 스스로 끄기는 '나오면 비정상'·'문제없음'만(값·사람 확인은 지문만으로 점검 불가).
- JQ-05(AI 문장 다듬기·자유 답 정리)는 다음 단계. 지금은 질문 틀 그대로 묻고, '판단 방법' 글은 기준과 함께 저장(관리 화면에 보임).
